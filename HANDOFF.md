## ORIGIN et CSRF en production locale (2026-11-04)

- **Symptôme** : « Cross-site POST form submissions are forbidden » sur `/inscription` et `/connexion` en build de production local, même avec `ORIGIN` renseigné.
- **Diagnostic** (sans lire aucun `.env` ; build de production dans `build-diag/`, serveur sur le port 4399, POST de formulaire avec des en-têtes `Origin` variés — résultats mesurés, pas supposés) : deux cas distincts. **Sans `ORIGIN`** : adapter-node suppose le schéma **https** — `Origin: http://127.0.0.1:3000` → 403, `Origin: http://127.0.0.1:4399` → 403, mais `Origin: https://127.0.0.1:4399` → accepté ; avec `ORIGIN=http://127.0.0.1:3000`, le même POST `http://127.0.0.1:3000` → 200. **Avec `ORIGIN=http://127.0.0.1:3000`** : naviguer via `localhost` (ou un autre port) envoie une origine différente de celle épinglée → 403. La protection compare schéma + hôte + port, chaîne exacte, à l’origine déduite de `ORIGIN`.
- **Correctif retenu** (consigne du propriétaire : **pas de liste d’origines autorisées** — une première version `STUDIO_COUTURE_ORIGINES_AUTORISEES`/`trustedOrigins` a été retirée) : avertissement au démarrage `avertirSiOriginAbsent` (`src/lib/server/config.ts`), appelé par `init` (`src/hooks.server.ts`) avec `production = !dev` de `$app/environment` — figé au build, car adapter-node ne définit pas `NODE_ENV` dans le processus (première version fondée sur `NODE_ENV` restée silencieuse, corrigée). En production sans `ORIGIN` : message console explicite (cause https supposé, exemple `ORIGIN=http://127.0.0.1:3000` en local), **jamais bloquant**, serveur démarré quand même (vérifié sur le build de diagnostic : avertissement affiché puis `Listening`). Protection CSRF inchangée, jamais désactivée. Tests unitaires ajoutés dans `config.test.ts` (avertit en production sans ORIGIN ; silencieux avec ORIGIN ou hors production ; validation complète non bloquante).
- **Documentation** : `README.md` (section « ORIGIN et CSRF (production) ») et `.env.example` (`ORIGIN`, nom sans valeur, avec commentaire — ajouté sans lire le fichier).
- **`STUDIO_COUTURE_BUILD_OUT` conservé** : `svelte.config.js` sort le build dans ce dossier si la variable est définie (défaut `build`, comportement inchangé) ; `playwright.config.ts` le respecte (`node <dossier>/index.js`) pour construire les e2e hors de `build/`.

## Parcours patron cliente : trois modèles à égalité, ordre unique, typage (2026-11-04)

- **Cause du formulaire vide** (page « Créer un patron pour <cliente> » parfois réduite au bandeau et au pied, jupe et robe surtout) : `validerMesuresPatron` (`src/lib/patterns/saisie-patron.ts`) **génère les pièces pendant la validation**, et les géométries brouillon jupe/robe lèvent une erreur pour des mesures individuellement dans les bornes mais mutuellement incompatibles (hanches < taille − 20, robe trop courte par rapport au dos, emmanchure). Dans `clientes/[id]/patron/nouveau/+page.server.ts`, cela donnait `mesures = null` avec `manquantes = []` (la fiche contenait déjà toutes les mesures) : **aucune branche de la page ne correspondait** (ni choix, ni formulaire court, ni salle), `<main>` se rendait vide. Le pantalon déclenche rarement ses gardes avec des valeurs usuelles, d’où le « parfois ».
- **Correctif** : la page a toujours une branche — mesures absentes de la fiche → formulaire court ; génération qui refuse → **formulaire complet prérempli + erreur traduite** ; l’action `completerMesures` relit et revalide toutes les mesures du modèle avant de continuer (enregistrement fiche seulement si demandé, sinon valeurs dans l’URL). Les formules marquées `a_valider` empruntent donc le même chemin visible pour les trois modèles au lieu d’une impasse.
- **Ordre d’affichage défini une seule fois** : `LISTE_MODELES` du registre = **pantalon large, robe fourreau, jupe droite** (deux colonnes : robe à droite du pantalon, jupe en dessous) — utilisé par la démo, le choix du modèle à la création, la fiche cliente et l’accueil.
- **Test e2e paramétré par modèle** `tests-e2e/patrons-modeles.spec.ts` : pour chacun des trois modèles, cliente complète → choix dans l’ordre du registre → salle avec aperçu → enregistrement sur la fiche → PDF commençant par `%PDF` ; plus le cas mesures refusées (formulaire de correction prérempli, jamais un écran vide) et l’ordre sur la démo publique.
- **Typage** : les 7 erreurs `npm run check` n’étaient **pas pré-existantes** (vérifié par worktrees détachés : 0 erreur à `585c71c` et à `b4d430b`) — elles venaient du chantier bilingue non commité (conversions chaîne→clé, paramètre `lang` ajouté). Corrigées sans changement de comportement, plus 6 avertissements de même origine (`$derived` manquants) : contrôle revenu à **0 erreur / 0 avertissement**.

## Correctif 413 sur l’upload photo (`BODY_SIZE_LIMIT`) (2026-10-28)

- **Bug réel (validation)** : en enregistrant les mensurations d’une cliente, page « 413 Payload Too Large ». **Diagnostic** : le formulaire mensurations (`src/routes/clientes/[id]/+page.svelte`) est un formulaire séparé, sans `enctype` multipart ni champ fichier — il n’envoie que `_csrf` et ses champs texte, il n’est donc pas en cause. Le coupable est l’upload photo : adapter-node plafonne le corps des requêtes à **512 Ko par défaut** (`BODY_SIZE_LIMIT`, lu dans `node_modules/@sveltejs/adapter-node/files/handler.js`), alors que l’application accepte des photos jusqu’à 5 Mo (`validerPhoto`, `src/lib/server/crypto.ts`). Toute photo > 512 Ko mourait en 413 avant d’atteindre le code.
- **Reproduction (avant correctif)** : le test Playwright étendu (photo de 4 Mo, puis photo de 5,5 Mo, puis mensurations seules) échouait — la page affichée était littéralement « 413 / Payload Too Large » (contexte d’erreur Playwright + pile `get_raw_body` du serveur construit).

La limite d’adapter-node est **globale, sans réglage par route** : le contrôle qui fait foi reste `validerPhoto` côté serveur (5 Mo, message « Photo trop lourde : 5 Mo maximum. » via `fail(400)`), et aucun autre formulaire n’accepte de fichier. Ajouté en plus sur la fiche cliente un **contrôle immédiat dans le navigateur** (même message, fichier rejeté avant envoi) : sans lui, un fichier de plus de 6 Mo heurterait quand même le plafond adapter-node en page 413 brute ; le contrôle serveur reste autoritaire si JavaScript est désactivé (entre 5 et 6 Mo, c’est lui qui répond en français).
